## Early architecture decisions (v0.1)

- **Language:** plain HTML/CSS/JavaScript (ES modules, `<script type="module">`). No framework or build step to start. If the UI later gets dynamic (reorderable or lockable results, swap-song buttons), Svelte was the suggested upgrade. The generator is UI-independent, so migrating is a UI-only rewrite.
- **Separation of concerns:** generator (pure logic) / settings UI / Spotify layer are separate. Anyone can use the settings page and generator without Spotify login; Spotify is only needed for the final "Save as playlist" step. Non-Spotify fallbacks: copyable title list, CSV download.
- **Master database:** a spreadsheet exported to CSV or JSON, committed in the repo and loaded at startup. One row per song: Spotify track ID, title, length, dance tags, other tags (e.g. tempo changes). Spotify is the catalog, playback, and playlist layer; this file is the source of truth for tags.
- **Settings:** one settings object; every control reads and writes it; the generator takes it as its only configuration input.
- **Persistence without a backend:** presets in `localStorage`, plus export/import of presets as JSON, plus optional shareable URLs encoding the settings. Per-user tag overrides are stored in the browser as `{ trackId: { tag: value } }` and merged over the base data at load. A backend (Supabase/Firebase/Cloudflare) is a later option only if cross-device sync or shared presets are wanted. Spotify login must not be used as the account system (see section 5).
- **Settings UI idea:** collapsible sections: Event basics, Categories and dances, Excursions (weights table), Fixed events, Repetition, Opening and closing. Controls: sliders, number boxes, checkboxes, dropdowns, `<details>`. Include "Reset to defaults" and input validation.

## Early vocabulary (generalized from the original ballroom README)

| Original | Now |
|---|---|
| Style (smoothStandard / rhythmLatin) | **Category** (any number N >= 1) |
| social dances (`social`, `timeToSocial`) | **Excursion** (`timeToExcursion` / `excursions.intervalMinutes`) |
| Line dance break | **Fixed event** (`dance`, `count`, `at`) |
| Paso Doble (`pasoLocation`) | **Fixed event** with `notAfter` restriction |
| `themeDances`, `fractionThemeMin/Max` | `theme.dances`, `theme.fractionMin/Max` |
| `earlyCount`, `earlyBlacklist` | `opening.earlyCount`, `opening.blacklist` |
| (new) collapsing similar dances | **Association** (`associations: [{ name, dances }]`) |

**Associations:** dances treated as one, e.g. "Waltz" = Smooth Waltz + Standard Waltz (9 Smooth/Standard dances become 5; Standard Quickstep stays unassociated). Applied before everything else: song tags and every dance named in the settings are renamed to the group name, so all rules see the merged dance. A one-member group is a rename. Each dance may be in only one association. The song database can therefore keep style-specific tags. **An association includes its own name by default** (e.g. "Waltz" = Waltz + Smooth Waltz + Standard Waltz); the UI adds it when an association is named, and old saved settings are upgraded once (settings `version: 2`).

**Competitive ballroom naming (from the developer, Oct 2026):** 19 dances in four styles (= categories): American Rhythm (Cha-cha, Rumba, Swing, Bolero, Mambo), American Smooth (Waltz, Tango, Foxtrot, Viennese Waltz), International Standard (Waltz, Tango, Viennese Waltz, Foxtrot, Quickstep), International Latin (Cha-cha, Samba, Rumba, Paso Doble, Jive). Standard form in the database: `<Smooth|Standard|Rhythm|Latin> <Dance>`. "American X" / "International X" / "Intl X" are translated (`canonicalDance` in site/js/shared/dance-names.js; applied when loading CSVs and in the library builder). Same-named dances are associated by default, **except** American (Rhythm) Rumba and International (Latin) Rumba, which stay separate; **American Bolero is associated with International Rumba**. A bare "Rumba" is ambiguous: the library builder asks which style. A bare "Tango" (no Argentine spelling such as "argentine", "tango argentino", "milonga") is guessed as ballroom Smooth + Standard Tango **but flagged for double-checking** (`DOUBLE_CHECK` in site/js/shared/dance-names.js); the builder offers "It's Argentine Tango" / "Ballroom is right" and warns before importing unconfirmed guesses. A bare "Waltz" (etc.) maps to both styles; a dance in only one style takes that style ("Quickstep" -> "Standard Quickstep").

Definitions: a **song** is a piece of music irrespective of dance; a **dance** is a categorical identity for bodily motions done to a song; a song may support several dances ("Oye Como Va is a cha-cha" is shorthand).

## Early summary of the rules (README.md was authoritative)

1. **Blocks:** categories alternate in blocks of 1..`maxInARow` songs (default 3). Block length is rerolled only after every category has had a turn. Interrupts (excursions, fixed events) do not reset the block.
2. **Shuffle-bag repetition:** within a category, no dance repeats until all of that category's dances have occurred; order is re-randomized each round (like Tetris bags).
3. **Spacing:** `minToRepeat` (default 4) songs must separate two songs of the same dance. Applies to theme dances too. The last song and fixed events are exempt.
4. **Excursions:** fire on a timer (every interval ± random variation, the first one too; not steered by the theme). Weighted reducing pool: each draw removes one occurrence of that dance. When every counter reaches 0, the pool **resets** to its starting weights.
5. **Fixed events:** e.g. a line-dance break at the halfway mark (3 songs), Paso Doble once at `at` 0.7. Two different fixed events are **never back to back** (general rule); `notAfter` adds extra per-event restrictions.
6. **Theme:** a theme is a set of dances and/or song tags (`theme.dances`, `theme.tags`, e.g. "Hollywood"); a song is a theme song if either matches. The theme share (`fractionMin`..`fractionMax`, default 50-70% for broad themes, 20-25% for dance-focused ones) is measured after the opening songs. **The current, complete theme rules are the agreed spec under v0.2.4 in section 9** (when a theme song is due, mixed themes, tag group, hidden theme category for standalone theme dances, theme minimum gap `theme.minGap`, openers = the opening songs, excursions not steered by the theme).
7. **Opening:** the first `earlyCount` (default 6) songs avoid `blacklist` (default Mambo / Salsa, Quickstep). With a theme they are also the theme openers; theme dances override the blacklist there.
8. **Closing:** an optional designated final dance. The night ends no later than `longest song - shortest song` past the target (and no earlier than one shortest song before it).

Original README "future work": scrape Spotify playlists, create Spotify playlists directly, in-place song replacement, a preferred-songs list spread evenly through the night, themed blocks of songs.

**Exists:** `site/js/generator/generator.js` (ES module), a pure-logic implementation of the rules with N categories:

- `generatePlaylist(songs, settings, options)` returns `{ playlist, totalSec, targetSec, overtimeSec, seed, warnings, stats }`.
- `validateSettings(songs, settings)` returns `{ errors, warnings }` (e.g. dance in two categories, missing songs, infeasible theme fraction).
- `checkRules(result, settings)` independently verifies a result against the rules (returns violations).
- Seedable PRNG (`settings.seed`) for reproducible runs.
- Simulation approach: it walks forward song by song with a clock, because the excursion timer, fixed events, and final-song budget depend on elapsed time. Each song needs `lengthSec`.
- If rules cannot all be met, it relaxes them in a fixed order (`LEVELS`) and records a warning rather than failing.
- Optional `options.songFilter(song, ctx)` hook for tag-based rules (e.g. no tempo-change songs in the opening).

Song format: `{ id, title, lengthSec, dances: ["Waltz", ...], tags: ["Hollywood", ...] }`.

Remaining design assumptions (not specified by the README):
- Theme share is steered by feedback (theme song due below `fractionMin`, avoided above `fractionMax`, otherwise due with probability = the midpoint); it can end a little below the minimum. - Fixed-event songs skip spacing rules (intended for line dances; themed blocks will not, see roadmap). A fixed event may directly follow an excursion.

Decided while coding: locked songs stand outside the category turns and excursion counts, and a dance with a locked song skips the shuffle-bag that night (like a theme dance; it keeps the gap) — otherwise a locked song coming up often jammed its category’s bag (41 of 200 test nights needed a rule relaxed with 3 locks; now none); a must-play song still waiting when the night is nearly over plays anyway (with a warning); Reset all also removes locks (it equals undoing everything). **Agreed spec (developer, Oct 2026):**
- **A. Lock rows and regenerate the rest** (also in the original plans: "lockable results").
  1. Every row of a generated playlist has a **lock** (🔒); a locked row keeps its song **and its place in the order** (#12 stays #12; start times shift). **Lock all** / **Unlock all** above the table.
  2. **Regenerate unlocked songs** makes a new playlist around the locked rows, following all the rules, with the locked songs counted as played (no repeats of them; the repeat gap is kept around them, before and after).
  3. A fixed event or block that would land on a locked place moves to the next free place (no warning).
  4. Locked songs that no longer fit before the end of the night are kept anyway, at the end (before the last dance).
- **B. Drag-and-drop reordering, and Undo.**
  5. Drag a row to move it (times and numbers update). Each row's actions also have **Move up / Move down** (dragging is fiddly on phones).
  6. A move that breaks a rule is reported as a **warning**, like other edits ("Warning: [reason]"); the move is always made.
  7. **Undo** next to Reset all, covering **every** edit (swap, insert, remove, restore, move, lock), with unlimited history: pressing it repeatedly walks back to the generated (or regenerated) playlist, which is what **Reset all** does in one step (locks included).
- **C. Moving blocks** (themed blocks **and** fixed events with several songs, e.g. the line-dance break).
  8. Whole blocks and the songs inside them can be moved. *Design choice (Claude):* an intact block shows a small header row with its name, a drag handle and Move block up / down, to move the whole block; dragging a single row moves just that song.
  9. **Intact** = its songs are still together (in any order, e.g. A-B-C-D → B-D-C-A): still a block, even if that breaks the rules it was made by. It is **modified** if its songs were reordered, swapped or removed (moving the whole block unchanged is not a modification); its name then shows "(modified)" **right away**.
  10. **Disbanded** = another song lands inside it, or its songs are scattered (A-B-E-C-D, B-D-E-F-G-C-A). Its songs are then labelled by their category, else "Excursion", else their dance (e.g. "Line dance"), and are **locked automatically** (part of the same edit, so Undo reverses both). On regeneration a disbanded block is **not** created again (no six line dances); if all its songs are unlocked, the next regeneration creates the block normally.
  11. Locking: if some songs of an intact block are locked and others not, regeneration drops the unlocked ones and **condenses** the locked ones into one shorter block (at the place of its first locked song), named "(modified)"; it is not refilled. An intact block with no locked songs is regenerated normally; one with locked songs is not created a second time.
- **D. A must-play list, spread evenly through the night** (from the original README's future work).
  12. Setting **Must-play songs**, with the same song picker as chosen-songs blocks (tag, work, dance, category, text).
  13. A must-play song plays only if its dance is **in a category, an excursion dance, or a standalone theme dance**; otherwise it never plays, and the settings warn about it.
  14. They are spread evenly after the opening and before the last dance, in **random order**: song i of k is due at about (i+1)/(k+1) of the night (4 songs: ~20%, 40%, 60%, 80%).
  15. When due, it plays at the first place where it fits the rules: a category dance on its category's turn, keeping the shuffle-bag and the gap; an excursion or standalone theme dance keeping the gap (an excursion dance does **not** use up an excursion count, and does not wait for the excursion timer). If it still does not fit after a few songs, it plays anyway, with a warning. It does not interrupt a block.
  16. As for chosen songs: never played elsewhere in the night, nor their duplicates (other versions may); may break the song length limits; unavailable ones are left out with a warning, or kept with a warning after the Spotify check; they count toward the theme share if they match. A must-play song that is also in a chosen-songs block plays in the block and counts for both.

  8. Songs are matched by which song is playing, not by counting, so going back, skipping or jumping works. A song not in the playlist: **Off the plan**, with its title, artist and dance (from the library if known, otherwise "—"); next is worked out from the last planned song played.
  9. Paused or nothing playing: "Paused", with the last song still shown. Not logged in or no permission: a message saying what to do.
  10. The Spotify credit on both layouts.
  11. **Program:** a **Print program** page and **Download program (Word)**: the song order (numbered) with each song's dance and special block names; no times. The Word document adds an empty **Song name** column for the organizer to fill in by hand. Song titles and artists are never included (Spotify's rule against permanent copies, as with the CSV removed in v0.3).
  12. **Check Spotify now** (Music runner): asks at once. A song **off the plan** can be **matched by hand** to a planned song ("It's #15 Line dance (the next song)", or any other from a list); both screens follow it from then on, for the night (forgotten on logging out). (Developer, after testing: some planned songs showed as off the plan. Cause, most likely: Spotify played another copy of the song under another ID ("relinking") and only says so when asked with the user's country; fixed by asking with market=from_token, the hand match is the fallback.)
  13. **Songs added during the night** (developer, after testing; replaces the earlier "no set dance button"): on the Music runner layout, a song off the plan can be **added to the night**: its title and artist come from Spotify; the organizer types its dance (suggested from the library, if known). It then shows as **Added**, with that dance, on both screens. Added songs never change the order: next stays the next planned song. Only the Spotify ID and the dance are kept, for the night (forgotten on logging out); the generator's playlist and the program are not changed.
